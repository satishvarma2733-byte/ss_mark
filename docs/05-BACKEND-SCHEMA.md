# Simply Sit — Backend Schema and Access Rules

Planning schema 1.0 · 25 October 2026. **Proposal, not a deployed migration.** Pair with `02-TRD.md` and `07-API-AND-STATE-MACHINES.md`. Physical tables are the proposed first sellable resource. Venue categories remain extensible for the broader hospitality-space proposition; supporting seats, overlapping zones or whole-space bookings requires a future physical-capacity model before enabling those resource kinds.

## Conventions and integrity

Unless marked `?`, fields are required/NOT NULL. All mutable entities have `id uuid PK default gen_random_uuid()`, `created_at timestamptz default now()`, `updated_at timestamptz default now()` and `version int default 1`. Update time/version through trusted database logic. Immutable events use only `id` and `created_at`. `FK` means a foreign key with `ON DELETE RESTRICT` unless explicitly stated. Monetary amounts are nonnegative `bigint` paise with `currency char(3)` constrained to `INR` for this pilot; rounding is deterministic and tested. Do not use float for money. Enum values below are application states backed by database checks/enums; unlisted values reject.

Every relationship carries sufficient scope to validate tenant ownership. Use unique `(id, venue_id)`/composite foreign keys for booking/resource/claim pairs and corresponding partner constraints; a booking cannot reference a resource from another venue. `jsonb` snapshots require validated versioned schemas and size limits; they are not unconstrained metadata bags. Public identifiers are random opaque references; UUID knowledge never grants access. Index all foreign keys used in lookups and tenant filters, then verify query plans with realistic seed data.

Customer owns their profile and bookings. Partner owns the business entity; active memberships govern staff access per venue, not every venue under that partner by default. A user can have multiple active venue memberships. Public listings expose a sanitized projection only; legal names, provider references, pending policies and verification evidence remain restricted. Food permissions are venue-specific; do not infer BYO entitlement from a category.

Relationships: one profile has many bookings, notifications, reviews, tickets and privacy requests; its Auth identity is an optional unique one-to-one link. One partner has many venues and payout batches. Profiles and venues are many-to-many through role-bearing venue memberships. A venue has many exclusive resources, policy versions, hours, media, amenities and tags; each resource has many rate versions and historical claims. Each booking belongs to one customer, venue and resource, has exactly one booking claim, and may have many sequential extensions/events/payment orders. An order has many actual payment attempts; each attempt has many refunds/disputes, subject to captured balance. Journals contain many entries and may reference a booking/payment/refund/payout. Payouts and earned booking allocations are many-to-many through payout_allocations; scoped keys preserve partner ownership throughout.

Illustrative invariant, **not complete executable migration**:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE inventory_claims ADD CONSTRAINT no_active_overlap
  EXCLUDE USING gist (resource_id WITH =, blocked_range WITH &&)
  WHERE (active);
-- Add checks for lower<upper, finite bounds, lower_inc=true, upper_inc=false.
-- Lock venue, then resource; transition due holds before inserting/replacing claims.
-- Membership/auth checks and all booking/claim writes belong in one transaction.
```

An active held claim blocks just as a confirmed claim does. Expiry is an explicit database update, not a view-only filter. A closure uses the same constrained table, expanded across affected resource IDs inside one transaction. Reject a closure overlapping held/confirmed/occupied inventory; return authorized conflicting booking references and require a separate reasoned service-cancellation flow. Schedule edits/retirement follow the same lock/check path. No manager override can bypass overlap integrity.

An extension widens its booking's existing claim to the requested end plus buffer while HELD; do not add an overlapping second claim for the same table. `bookings.end_at` stays unchanged until APPLIED. Expiry/failure shrinks the claim to the current committed end plus buffer. If a competing next reservation prevents widening, return conflict before charging. Expired original holds release `active=false`; extensions never release their original confirmed booking.

Ledger balance and payout arithmetic require a finance-reviewed posting policy. At capture, record gateway receivable and customer booking liability. On earned/reconciled completion, move liability into approved partner/platform/tax allocations. A cancellation reserves customer refund liability and reduces the corresponding available allocation; a processed provider refund clears that liability. Gateway fees, settlements, chargebacks and reversals each need separate evidenced journals. Never compute available partner payout as booking totals alone. Funds tied to unresolved refunds/disputes/unknown operations stay reserved. A submitted refund/payout cannot be marked processed/paid without provider evidence. A single order with a failed payment followed by a successful payment must retain both attempts; provider order identity is not a payment identity.

## RLS and action authorization matrix

Legend: R = scoped read; W = limited write through validated service/procedure; — = deny. “Service” is the trusted domain service/worker with explicit actor checks. Direct client writes to bookings, claims, money, memberships, published policies, outbox and audit are denied. Authorization must be checked inside mutation transactions, with membership rechecked rather than relying on stale JWT roles.

| Record group | Public | Customer | Assigned staff | Assigned manager/owner | Support admin | Finance admin | Superadmin / service |
|---|---|---|---|---|---|---|---|
| Approved catalogue/reviews | R | R | R | W scoped draft/profile | R/moderate | R | approve/pause via W |
| Own profile/notification | — | R/W safe own fields | own only | own only | masked case-scoped R | — | audited support action |
| Partner identity/provider refs | — | — | — | scoped masked R | masked case R | R | W provider setup |
| Memberships/roles | — | own R | own R | invite/revoke STAFF scoped; owner transfer protected | — | — | role grants audited W |
| Hours/rates/policies/resources | published projection | published projection | operational R, readiness W | scoped W with conflict checks | R | rate snapshot R | W with audit |
| Booking/payment summary | — | own R/actions W | scoped minimal operational R/W | scoped operational R/W | case-scoped R/remedy proposal | financial R/refund W | W through state machine |
| Raw claims/quotes/events | — | own safe quote/booking projection | scoped calendar projection | scoped calendar projection | case R | finance projection | service W |
| Refund/ledger/payout/reconciliation | — | own refund projection | — | scoped financial report R | masked status R | R/W approved money actions | service posting only |
| Support/incident | — | own R/W | report scoped incident; restricted case R | scoped nonsensitive R | assigned-case R/W | payment-case R | sensitive-case authorization |

Use `auth.uid()` to resolve an active profile through profiles.auth_user_id, then explicit active memberships for scoped access; never assume the stable profile ID is the Auth ID. Safe helper functions use a fixed `search_path` and narrowly granted execution rights. Test SECURITY DEFINER functions for bypass and recursive-policy issues. RLS is not column masking: create safe views/select projections and revoke unsafe base-table grants. Service credentials bypass RLS, so worker tests must prove its application tenant checks as well. Storage buckets: approved public venue images only; private exports require ownership-scoped signed access and automatic expiry. Privacy requests are own-read/request-only for customers and fulfillment-only for authorized superadmin/privacy capability; they do not expose other users' exports.

## Auth lifecycle, deletion and migration

OTP request → generic response → provider verification → verified Auth user → upsert minimal profile/record accepted terms → authenticated session. Protected mutations revalidate user, active profile and membership. Expired session returns 401 with preserved safe draft; client signs in then requests a new quote. Revocation takes effect before the next protected write. Sign-out clears session/cached private data. Lost email access needs a documented verified support process; support cannot simply change identity based on a booking reference. Email changes require provider reverification. Account deletion first cancels/remedies active commitments, prevents new bookings, anonymizes personal fields, removes auth identity where eligible and preserves required pseudonymous finance/audit records without cascading away ledger evidence.

**Proposed retention, subject to owner/legal approval before production:** unconsumed quotes seven days; expired hold records ninety days then minimize; idempotent HTTP response cache seven days with permanent money operation keys/journals; sanitized provider event detail ninety days, identifiers/hash one year; operational logs thirty days; precise search coordinates discarded after the request; aggregate anonymous analytics retained; resolved support content one year unless sensitive cases need shorter retention/legal hold. Proposed finance/booking/audit evidence eight financial years requires professional confirmation and a documented legal basis. Backups rotate on the selected provider plan; erasure documentation states the real backup expiry, restores reapply deletion tombstones, and legal holds suspend relevant purge. Do not enable an automatic statutory purge based solely on these proposed durations.

Migration sequence: identity/tenant catalogue → versioned policies/rates → bookings/claims/exclusion → money ledger/refunds → jobs/events → RLS/grants/storage → support/reports. Each migration has schema/type changes, existing-row backfill, constraint validation and rollback/forward-repair notes. Test from an empty database and a prior-version snapshot; do not edit applied migrations. Seed staging with fictional venues, capacity, photos with rights, policy/rate fixtures, holiday closures and auth fixtures; no real personal/bank data. Fixed test IDs are environment-specific and never grant production privileges. Record extension availability and exclusion operator support on the selected PostgreSQL instance.
