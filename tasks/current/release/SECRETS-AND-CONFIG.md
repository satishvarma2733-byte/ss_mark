# Secrets and configuration inventory (names only, no values)

Prepared 3 November 2026 from the code (`process.env` reads in apps and packages) and the TRD provider table. Every
environment (development, staging, production) gets its own values; nothing is shared between them (TRD s.7). Values
are created and held by the owner's organization accounts; this session created none outside the local stack.

## Server: web/API (Next.js) and worker

| Name | Kind | Used by | Today (local) | Production source and owner |
| --- | --- | --- | --- | --- |
| `DATABASE_URL` | Secret | web, worker, scripts | Local Supabase Postgres | Supabase project (Mumbai), pooled connection for web, direct for worker; owner's Supabase org |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | Public | web server (Auth) | Local CLI keys | Supabase project settings |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Public (bundled) | web browser | Same as above | Same; must never hold a secret (enforced by `loadServerEnv`) |
| `NEXT_PUBLIC_APP_URL` / `APP_URL` | Public | payment return URLs, links | `http://localhost:3000` | Production web origin (HTTPS) on the owner's domain |
| `APP_ALLOWED_ORIGINS` | Config | same-origin check for cookie writes | localhost | Production web origin only |
| `APP_ENV` | Config | environment label | development | `production` |
| `APP_MODE`, `PAYMENT_PROVIDER`, `EMAIL_PROVIDER`, `MAPS_PROVIDER` | Config | provider selection | `mock` (only value accepted today) | Live adapters are not built; D04 picks the payment provider, then an adapter replaces the mock |

| `ARRIVAL_CODE_SECRET` | Secret | arrival QR/PIN derivation (web, worker); venue invitation link tokens (worker, own HMAC label, M5.1 F1) | Generated locally | Random 32+ bytes per environment; rotating it invalidates the arrival codes of upcoming bookings and the links of open invitations (managers resend them), so rotate only with a re-issue plan |
| `NATIVE_MIN_VERSION` | Config | booking-creating routes, admin page | Unset (e2e: 0.1.0) | Unset at launch; raised only through an approved recovery plan (RUNBOOK s.5) |
| `WORKER_ID`, `WORKER_TICK_MS`, `WORKER_BATCH_SIZE`, `WORKER_LEASE_SECONDS` | Config | worker | Defaults | One worker per environment for the pilot; unique `WORKER_ID` per process |
| `BOOTSTRAP_CONFIRM_REMOTE` | Guard | bootstrap script | Unset | Set only for a deliberate, owner-approved first-admin bootstrap of a hosted project |
| `MAILPIT_URL` | Local only | tests read OTP emails | Local Mailpit | Not used outside tests |

Supabase Auth settings of each hosted project (launch gate, M5.1 review F1): **Confirm email ON** (local
`supabase/config.toml` `[auth.email] enable_confirmations = true`), "secure email change" ON (`double_confirm_changes`),
anonymous sign-ins off. With confirmation off, a password sign-up or email change through the public Auth API marks an
address confirmed without any email being opened. Invitations also need the emailed link token, but customer accounts
rely on this setting. Password sign-in is not used by the OTP-only pilot; blocking password sign-ups outright (Auth hook)
is an open follow-up.

Not configured anywhere yet (needed before launch): Auth SMTP sender (Resend or SES, set in Supabase Auth settings, D09),
error/crash monitoring DSNs (Sentry, TRD; no SDK is integrated yet), real maps provider key (TRD; the app links to
OpenStreetMap today), payment provider credentials and webhook endpoint (D04).

owner's accounts (EAS-managed or owner-held). The local Android project still signs release builds with the debug key.

`20261103000800_m5_operational_purge`, `20261103000900_m6_release_switches`, `20261103001000_m51_invitation_tokens`.
All are additive except the last, which replaces `app.accept_invitation(uuid, uuid)` with
`app.accept_invitation(uuid, text, uuid)` (the emailed token) and expires open invitations that have no token.

- Applied in sequence on an empty database by every `pnpm db:reset` (last: 3 Nov 2026); restore drill 28/28 (M5).
- `supabase/seed.sql` is **local synthetic data only** and must never run against staging or production. It also opens
  the release switches; a production database starts with BOOKINGS, EXTENSIONS and PAYOUTS closed.
- Production needs a reference-data step that seed does not provide: approved fee configuration (D02/D04), current
  terms and privacy versions, real venues through partner onboarding, first superadmin (bootstrap script, guarded).
- Rollback is restore or forward fix (docs/06); no down migrations.
