## F1 (High): an email can be claimed without mailbox proof, enabling invitation takeover and account pre-hijack

**Status (3 Nov 2026): fix written by the reviewer session; retest pending. F1 stays open until the integration and
e2e suites pass.**
- `supabase/config.toml`: `enable_confirmations = true`. The running local Auth container still has auto-confirm
  until the stack is restarted (`supabase stop && supabase start`), which was not done on the shared stack.
- `supabase/migrations/20261103001000_m51_invitation_tokens.sql` (applied locally with `supabase migration up`):
  - adds `venue_invitations.token_hash`;
  - adds a worker-only `app.record_invitation_token`;
  - replaces `app.accept_invitation(uuid, uuid)` with `(uuid, text, uuid)`, which requires the emailed token and
    otherwise returns NOT_FOUND;
  - expires open invitations that have no token.
  Read-only check: the old signature is gone; EXECUTE is held by authenticated (accept) and simply_worker (record)
  only, and PUBLIC is closed.
- The token is derived as `packages/domain/src/invitation.ts`: HMAC-SHA256 of the invitation ID under its own label,
  keyed with `ARRIVAL_CODE_SECRET`, and only its SHA-256 is stored. The worker (`apps/worker/src/loop.ts`) records
  the hash and then sends the link (`EmailMessage.values.accept_path`).
- The web side requires the token: `POST /api/v1/invitations/{id}/accept {token}`, contract `invitationAcceptSchema`.
  The partner home keeps `?invitation=&token=` through sign-in, and shows Accept only for the linked invitation.
- Tests added or changed:
  - unit: `packages/domain/src/invitation.test.ts`;
  - integration: `tests/integration/partner-operations.test.ts` covers no token yet, a wrong token, another account
    holding the token, a non-worker recording a hash, and accept plus replay;
  - e2e: `apps/web/e2e/partner.spec.ts` with `deliverInvitationLink`;
  - release note: `tasks/current/release/SECRETS-AND-CONFIG.md` (hosted Confirm email is a launch gate).
- Checks: `pnpm typecheck`, `pnpm lint`, `pnpm test:unit` (78/78) and a typecheck of the changed test files pass.
  The integration and e2e runs were not executed: the shared-stack test run was refused in this session pending user
  confirmation.
- Still open from the suggested fix: blocking password sign-ups outright with an Auth hook. Account pre-hijack is
  closed by confirmations only once Auth runs with the new setting.

**Where**
- `supabase/config.toml:236`: `[auth.email] enable_confirmations = false`. The running auth container has
  `GOTRUE_MAILER_AUTOCONFIRM=true`, `GOTRUE_EXTERNAL_EMAIL_ENABLED=true` and `GOTRUE_DISABLE_SIGNUP=false`.
- `supabase/migrations/20261103000100_partner_operations.sql:1113-1121`: `app.my_auth_email()` treats
  `auth.users.email_confirmed_at is not null` as proof that the caller owns the address.
- `supabase/migrations/20261103000600_m4_review_fixes.sql:160-196`: `app.accept_invitation()` grants the invited
  STAFF or MANAGER role to whoever's `my_auth_email()` equals the invitation email (line 173). No secret from the
  invitation email is required (see the table comment at `...0100_partner_operations.sql:33`).
- `apps/web/app/api/v1/auth/mfa/enroll/route.ts:39-54`: the first TOTP enrolment needs only an aal1 session.

**Why it fails.** The pilot is meant to be email-OTP only (docs/02 l.88). Supabase Auth, however, still accepts
`POST {SUPABASE_URL}/auth/v1/signup {email, password}` with the public publishable key. With auto-confirm on, it
creates the user with `email_confirmed_at` set and returns a session, without any email being opened. The same
setting very likely also applies `updateUser({ email })` changes immediately. That is GoTrue's documented auto-confirm
behaviour, but I did not exercise it.

**Failing scenario 1: invitation takeover**
1. The owner of Venue A invites `newmanager@cafe-a.test` as MANAGER, through `app.partner_invite`.
2. That address has no Auth account yet. An attacker who knows or guesses it calls `/auth/v1/signup` with that email
   and any password. The account is created confirmed, and the trigger creates a profile.
3. The attacker's session calls `GET /api/v1/invitations`. `my_invitations` matches by email and lists Venue A, and
   `POST /api/v1/invitations/{id}/accept` succeeds.
4. The attacker enrols their own TOTP (aal1 is enough for a first factor), reaches aal2, and is now MANAGER of
   Venue A. They can see bookings and prices, change rates, hours and policy drafts, invite staff, and service-cancel
   bookings.

**Failing scenario 2: account pre-hijack**
1. An attacker signs up `customer@example.test` with a password before the real person ever uses the service.
2. Later the real person signs in with an email OTP and lands in the same Auth user, so the same profile.
3. The attacker can still sign in with the password. They can read that person's bookings and arrival codes, and can
   cancel bookings (after the M2 R2 terms check).

**Suggested fix**
- Set `enable_confirmations = true` locally, and record the same setting as a launch gate in
  `tasks/current/release/SECRETS-AND-CONFIG.md` for the hosted project. Also consider `secure_password_change = true`.
- Since the pilot is OTP-only, also block password identities: use a Supabase "before user created" Auth hook to
  reject sign-ups with a password, or have `app.require_active_profile()` / `app.my_auth_email()` reject
  `auth.users` rows with a non-empty `encrypted_password`.
- Make invitation acceptance prove mailbox possession: email a random single-use token, store only its hash on
  `venue_invitations`, and require the token in `accept_invitation`. Matching the email alone stays as a second check.
- Add regression tests: a password sign-up is refused; an invitation cannot be accepted without its token.

## F2 (Medium): platform-role RLS reads and Storage reads skip the TOTP check

**Where.** These are the current policies (`pg_policies`), defined in
`supabase/migrations/20261026001000_rls_initplans.sql`:

| Table | Line | Roles that can read without aal2 |
| --- | --- | --- |
| `audit_events` | 143 | SUPERADMIN: every column, including `reason` and `safe_diff` |
| `profiles` | 95 | SUPPORT, SUPERADMIN |
| `platform_memberships` | 107 | SUPERADMIN |
| `venue_memberships` | 100 | SUPERADMIN |
| `inventory_claims` | 122 | SUPERADMIN |
| `partners` | 84 | SUPPORT, FINANCE, SUPERADMIN |
| `fee_configurations` | 90 | FINANCE, SUPERADMIN |
| `venue_policies` | (same file) | SUPPORT, SUPERADMIN, all drafts |

The `app.visible_venue_ids()` admin branch (line 33) exposes every DRAFT, PENDING_REVIEW and REJECTED venue, with its
resources, rates, hours and media, to SUPPORT and SUPERADMIN. Storage read policy `app.media_object_readable`
(`...0100_partner_operations.sql:1580-1592`) lets venue members and SUPPORT read unapproved photos at aal1.

By contrast, the M2 R1 fix gated venue-member reads (`app.my_venue_ids` requires aal2), and finance tables use
`app.is_finance_reader()` (aal2).

**Failing scenario.** Someone obtains a superadmin's email OTP (phishing, or a shared inbox) and gets an aal1 token
without the TOTP. They call `GET http://<supabase>/rest/v1/audit_events?select=*` with the publishable key and that
token. They receive the full audit trail, including contact-reveal reasons, membership grants with profile IDs and
refund reasons. `/rest/v1/profiles` returns every profile. The portal pages would have demanded TOTP first. The REST
gateway is reachable: an anonymous `GET /rest/v1/venues` returned 200 locally.

**Suggested fix.** Add `app.is_platform_reader(p_roles text[])`, returning
`app.current_aal() = 'aal2' and app.has_platform_role(p_roles)`, mirroring `is_finance_reader`. Use it in every
policy above, in `visible_venue_ids()` and in `media_object_readable()`. Extend `tests/integration/rls.test.ts` with
aal1 platform-role tokens for each table.

## F3 (Medium): Support can approve listings and policies and issue full-refund service cancellations

**Where**
- `supabase/migrations/20261103000100_partner_operations.sql:90`: `require_platform_admin()` defaults to
  `['SUPPORT','SUPERADMIN']`, and that default is used by `admin_review_venue` (l.906), `admin_review_policy` (l.978)
  and `admin_review_media` (l.1018).
- `supabase/migrations/20261102000200_cancellation.sql:249-252`: `service_cancel_booking` lets SUPPORT cancel any
  CONFIRMED booking with `venue_cancel_refund_bps`, a 100% refund.
- `supabase/migrations/20261103000300_support_reviews.sql:482-529`: booking search by ref, venue, date or email is
  open to SUPPORT without a ticket.

**Expected.** The docs/05 RLS matrix says support may "R/moderate" the catalogue, while the superadmin does
"approve/pause". For bookings, support does "case-scoped R/remedy proposal" and finance does "refund W". docs/02 l.92
says "support admins investigate and propose remedies; superadmins approve membership and listings".

**Failing scenarios**
1. A support admin approves a live venue's policy draft that sets `late_refund_bps = 0` and
   `cancel_cutoff_minutes = 2880`. New customers get those terms with no superadmin decision.
2. A support admin service-cancels a friend's confirmed booking shortly before it starts. The customer gets 100% back,
   while the venue (which may well have honoured it) earns nothing (gross 0 at `recognize_booking_earning`). No
   finance person is involved.

**Suggested fix.**
- Restrict `admin_review_venue` and `admin_review_policy` to SUPERADMIN. Media moderation can stay with support.
- Make platform service-cancel FINANCE/SUPERADMIN only, or have SUPPORT create a remedy proposal that finance applies.
- If the owner wants the current behaviour, record it in the decision register and update docs/05, so code and spec
  agree.

## F4 (Medium): session-long aal2 for privileged money actions; single-person admin refunds

**Where**
- `app.require_aal2()` (`supabase/migrations/20261026000600_auth_helpers.sql:200-211`) checks only the session's
  `aal`. A Supabase session stays aal2 across refreshes for the whole refresh-token lifetime.
- That check is all that guards:
  - `admin_refund` (`20261103000600_m4_review_fixes.sql:299`)
  - `approve_payout_batch` and `mark_payout_batch`
  - `admin_set_release_switch` (`20261103000900_m6_release_switches.sql:185`)
  - `admin_grant_venue_membership`
- `admin_refund` inserts the refund with `approved_by = null` and queues `refund.submit` immediately
  (`m4_review_fixes.sql:373-376`). It is single-person, up to the full refundable capture, and after earning it can be
  charged to PARTNER.
- docs/02 l.92: "Require MFA and recent reauthentication for privileged actions, refund approval and payout-detail
  changes." Only `app.request_privacy` checks recency, using `amr` timestamps.

**Failing scenario.** A finance admin verified TOTP on Monday and left the browser session open. On Thursday, someone
with access to that browser issues admin refunds of the full captured amount on several finished bookings with
`charge_to = PARTNER`. That drives the partners' payables negative, which nets against their next payouts, and no
second person or fresh TOTP is needed. The same session can also reopen BOOKINGS or PAYOUTS.

**Suggested fix.**
- Add `app.require_recent_mfa(p_minutes integer default 10)`. It requires an `amr` entry with method `totp` and a
  timestamp within the window, as `request_privacy` already does for `otp`. Call it from `admin_refund`,
  `admin_retry_refund`, payout approve and mark, fee approval, `admin_set_release_switch` and role grants.
- Decide (owner and finance) whether admin refunds above a threshold need a second approver. If so, add a REQUESTED,
  then APPROVED, then submit step with `approved_by <> requested_by`.

## F5 (Low): reconciliation coverage can rely on a run that finished before the capture was recorded

**Where.** `supabase/migrations/20261103000600_m4_review_fixes.sql:600-617`. Coverage is decided by
`r.period_from <= a.captured_at < r.period_to`. The value of `a.captured_at` is the provider's timestamp
(`coalesce(p_captured_at, v_now)` in `apply_payment_observation`), not when we learned of the capture.

**Failing scenario.**
1. The provider captures payment P at 10:00, but its listing API lags.
2. Finance runs reconciliation over 09:00 to 11:00 at 11:05. The provider list does not yet include P, there is no
   local record yet, and the run is MATCHED.
3. At 11:20 a webhook records P with `captured_at = 10:00`. It is allocated to booking B, which completes, and B's
   earning goes into a payout batch.
4. `approve_payout_batch` treats P as covered by the 11:05 MATCHED run, which never compared P.

**Suggested fix.** Add `and r.completed_at > a.created_at` for capture points, and `r.completed_at > f.processed_at`
for refund points. Equivalently, carry a local `recorded_at` and require the run to start after it.

## F6 (Low): payout batches ignore partner status and `payout_enabled`

**Where.** `supabase/migrations/20261103000400_finance.sql:964` checks only that the partner exists. Neither
`create_payout_batch` nor `approve_payout_batch` (`m4_review_fixes.sql:567`) checks `partners.status` or
`partners.payout_enabled`.

**Failing scenario.** A partner is SUSPENDED, or has never completed payout onboarding (`payout_enabled = false`).
Finance drafts a batch, a second finance admin approves it, and it is marked PAID. The ledger now shows a payout to a
partner that should not receive money.

**Suggested fix.** Require `status = 'APPROVED' and payout_enabled` in both functions, failing with
`PAYOUT_NOT_ENABLED` or `INVALID_TRANSITION`.

## F7 (Low): customers can read commission terms from their own rows through the REST gateway

**Where.** `supabase/migrations/20261026000900_rls_grants.sql:103` grants every column of `quotes`, and l.106-109
grant `bookings.price_snapshot` to `authenticated`. The own-row policies allow customers to read them. The snapshot
holds `commission_bps`, `platform_fixed_paise` and `rounding_rule`. `apps/web/lib/price.ts` (review F7) strips those
fields in the API, but the REST gateway serves the raw column.

**Failing scenario.** A customer calls `GET /rest/v1/bookings?select=price_snapshot` with their own token and reads
the platform commission for that venue.

**Suggested fix.** Revoke `price_snapshot` from the `authenticated` column grants on `bookings` and `quotes`, and keep
customer reads on the API projections. Alternatively, expose a customer view without the internal keys.

## F8 (Low): one failing worker step stops reconciliation; batch leases are not renewed

**Where.** `apps/worker/src/loop.ts:178-215` and `apps/worker/src/index.ts:24-25`.

**Failing scenarios**
1. All tick steps share one `try`. If `expireDueHolds`, `leaseJobs`, `recognizeEarnings` or `purgeOperationalData`
   throws on every tick, `reconcile()` and `reconcileRefunds()` never run, for example because of one row that
   violates a constraint, or a lock timeout under load. Missed webhooks then stop being recovered for every order,
   and stalled refunds are no longer re-submitted. Only the missing reconcile counters would show it.
2. Up to 10 jobs are leased together for 60 s and run one after another. With several slow provider calls (for
   example `refund.submit` timing out at 10 s or more each), later jobs' leases lapse before they start, and a second
   worker leases and runs them at the same time. The handlers are idempotent (operation keys, business keys), so the
   outcome is correct today. The design does, however, rely on every future handler being idempotent, and it doubles
   provider calls.

**Suggested fix.**
- Wrap each tick step in its own try/catch with its own error counter in the heartbeat.
- Lease one job at a time, or extend the lease (`lease_until = now() + lease`, checked against `leased_by`) right
  before running each job.

## F9 (Low): deletion pending blocks the customer's own cancellations

**Where.** `app.cancel_booking` (`supabase/migrations/20261102000200_cancellation.sql:190`) and `app.cancel_hold` call
`app.require_active_profile()`, which raises `ACCOUNT_DELETION_PENDING` (`20261026000600_auth_helpers.sql:146-147`).
`app.request_privacy('DELETE')` sets `DELETION_PENDING` at once
(`20261026000800_account_jobs_functions.sql:96-98`), and nothing reverses it.

**Failing scenario.** A customer has a confirmed booking for next week under a 100% early-refund policy. They request
account deletion and then try to cancel. The cancel fails, and once the cutoff passes their refund falls to
`late_refund_bps` (pilot: 0) unless support steps in.

**Suggested fix.** Let `cancel_booking` and `cancel_hold` run for DELETION_PENDING profiles, using a helper that
accepts ACTIVE or DELETION_PENDING but not SUSPENDED or ANONYMIZED. Keep new commitments blocked. Mention this in the
deletion confirmation copy.

## F10 (Low): M6 switch edges

**Where**
1. `apps/web/lib/service-status.ts:16`: `if (!minimum || header === null) return;`. Any request without
   `x-simply-sit-client` is treated as an up-to-date web client, including bearer-token (native) requests. A native
   build that predates the header, or a modified client, starts holds, checkouts and extensions after
   `NATIVE_MIN_VERSION` is raised. A malformed header is correctly refused, because unparseable counts as older.
2. `supabase/migrations/20261103000900_m6_release_switches.sql:185`: one FINANCE admin can reopen PAYOUTS after a
   superadmin closed it for an incident. Approval still needs two finance people, but the incident hold itself is a
   one-person decision.
3. Nit: `v_switch.version <> p_expected_version` (l.196) lets a NULL expected version through. The API contract
   requires an integer, so this is reachable only by direct SQL.

**Suggested fix.**
- When `identity.via === "bearer"` and `NATIVE_MIN_VERSION` is set, refuse a missing header with `UPDATE_REQUIRED`.
- Decide whether reopening PAYOUTS should be SUPERADMIN-only, or whether whoever closed it must reopen it.
- Use `is distinct from` for the version check.

## Areas checked with no issue found

- **M6 release switches.** Every insert into `quotes`, `bookings`, `payment_orders` (booking and extension) and
  `extension_requests`, and every move to HELD, goes through a guard trigger. I grepped all 8 insert sites, and the
  triggers are table-level, so new code cannot bypass them. The payout guard covers APPROVED and PROCESSING, and
  recording an APPROVED batch as PAID stays possible, as documented. In-flight payment orders, confirmations, late
  captures, refunds, arrivals and reconciliation are unaffected, as intended. BOOKINGS and EXTENSIONS are
  SUPERADMIN-only, with aal2, a reason, an audit row and optimistic versioning. `service_status` returns only
  booleans. Each statement re-reads the switch in READ COMMITTED.
- **Exclusive inventory.** The `no_active_overlap` exclusion constraint is backed by explicit expiry inside the lock
  path. The lock order is venue, then resource, then booking (then order, attempt, refund) in `lock_booking`,
  `create_booking_hold`, closures, `lock_venue_inventory`, extensions, check-in and out, no-show and cancellation. The
  multi-venue sweep (`expire_due_holds`) locks in sorted order. `recognize_earnings` takes only booking locks, with
  SKIP LOCKED. I found no lock cycle, including with the partner-payable advisory lock. Closures, hours, capacity and
  retire all refuse when they conflict with a live claim.
- **Extensions.** The claim widens by UPDATE under the exclusion constraint while the resource is locked, and shrinks
  back on expiry, cancel and check-out. Only an exact, timely capture on a HELD or PENDING_PAYMENT extension of a
  CHECKED_IN booking moves `end_at`, which `guard_booking` allows only to that extension's requested end. Anything
  else becomes a refund liability.
- **Immutable snapshots.** `guard_booking` blocks price, policy, identity and start changes. A changed rate or policy
  between quote and hold returns `QUOTE_CHANGED`. Fee configs are future-dated and need two people. Each rate pins its
  `fee_config_version`. Published policies never change, and a draft is frozen while its venue is under review (the
  M4 F5 trigger).
- **Payment verification.**
  - Only `process_payment_observation` (worker role, `is_worker()`) can confirm a booking. Client and redirect hints
    only choose which payment to fetch from the gateway.
  - The order, provider and environment must match. An amount or currency that differs, or changes, is quarantined.
  - A late capture after expiry or cancellation becomes a full refund liability, and the hold is never revived. A
    duplicate capture becomes one full refund per attempt (unique operation key). Attempt state never regresses.
  - An uncertain order creation becomes UNKNOWN and is reconciled before anything new is created, looked up by
    receipt. A verify call never creates orders.
  - The webhook HMAC is checked over the raw, size-capped body before parsing; events are deduplicated and only
    allowlisted fields are stored.
- **Refunds.** `guard_refund` enforces the ceiling under the attempt lock. Cancellation and no-show refunds are capped
  by the remaining booking liability (M4 F1). A FAILED refund is retried once per row (unique `retry_of`) with no new
  journal. `refund_reserved` stops an admin refund from double-paying around a FAILED refund. UNKNOWN and PROCESSING
  refunds are re-submitted with the same operation key. PROCESSED requires a provider refund ID.
- **Earnings, payouts and ledger.**
  - An earning is recorded at most once (unique `booking_id`, plus the queue).
  - Payouts need two people (creator differs from approver, checked in the function and by a constraint). The
    partner lock, the re-check of available payable, per provider and environment reconciliation coverage (apart from
    F5), the freeze on a newer MISMATCH, PAID requiring evidence plus a journal, and FAILED releasing allocations all
    hold.
  - Journals must balance (deferred trigger) and are append-only.
- **Tenancy.** `require_venue_manager` and `require_venue_staff` re-check membership and aal2 inside each
  transaction. I found no cross-venue path, because every partner function resolves the venue from the target row.
  Staff cannot reach manager-only actions (rates, hours, policy, closures, revoke, statements). Only owners can invite
  or revoke managers, or retire tables, and the last owner cannot be removed. Confidential tickets are visible only
  to superadmins and the assigned admin. Each contact reveal needs a reason and is audited. Finance tables use aal2.
- **Auth and session.**
  - Exactly one identity source per request. Bearer tokens are validated with `auth.getUser`, and claims come only
    from the validated token.
  - Cookies are httpOnly and SameSite=Lax, and cookie writes need a matching Origin.
  - MFA verify is web-session only. Every app.* write re-checks the active profile.
  - Idempotency is scoped per auth user, route and key, in the same transaction as the write.
  - The only dynamic SQL is the fixed role literal in `inRole`.
- **Worker.** Leasing uses SKIP LOCKED. Only the current lease holder can complete or fail a job, and exhausted jobs
  go DEAD. Handlers are idempotent (but see F8). The purge removes only expired idempotency records and unbooked
  quotes more than 7 days past expiry.
